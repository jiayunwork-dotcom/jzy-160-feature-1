试验台那边想把橡胶隔振垫的长期服役监测接进来：传感器每隔一阵送来一小批应变采样和当时的温度，他们希望马上拿到这批采样对应的应力，并且服务要记住到目前为止的整段加载史，下一批来了接着往下算，而不是每次把几个月的完整历程重新提交一遍。现在的作业接口只会一次收下一条完整历程、算完就结束，应付不了这种一直往后延伸的用法。

这次要加的是「跟踪通道」。开通道时指定一个已有的材料档，通道从未加载的静止状态起步，也可以给一个初始应变瞬时施加。之后客户端按批次往通道里追加数据，每批是时间上紧接上一批末尾的一串采样点（时间、应变、温度），批次带客户端自己编的连续序号。服务算出这批里每个采样时刻的应力和当时的平移因子并返回，同时把通道推进到这批末尾。通道当前推进到哪一刻、末尾的应变和温度，以及下一批能直接接着算所需的全部状态，都要落进 MongoDB；应用重启以后继续追加，结果和没重启一样。

通道里的温度随采样变化，不再是整条历程一个常数。材料档带 WLF 参数时，变温下的松弛按时温等效累积：高温那段时间松弛走得快，低温时走得慢。两个相邻采样点之间温度怎么看待、这段时间折合成多少等效时间，合理的处理不止一种，由你来选，并在 README 里写明选了哪种、为什么、温度变化剧烈时误差会怎样。材料档没有 WLF 参数时，温度只记录，不参与计算。

监测链路会重发，也会乱序。同一序号的批次再次送来，内容相同就原样返回上次的结果、不重复推进；内容不同要拒绝并指出冲突。序号跳号、或者批次起点早于通道当前时刻，同样拒绝，通道状态不能因此被改动。同一个通道可能被两个采集进程同时追加，最后必须等价于按序号逐批处理：不能两批都基于同一个旧状态往前推，也不能丢掉其中一批；不同通道之间互不阻塞。

分析员还想问「要是从那时起换一种加载会怎样」：指定通道里一个已经推进过的时刻（落在某一批的末尾即可），从那里分叉出一条新通道，新通道继承那一刻的状态，之后独立追加，原通道不受影响。这就需要留历史检查点。每批都存一份，存储随批次线性增长；只存稀疏检查点，分叉时就得从最近的检查点重放后面的原始采样，原始采样也得留着。保留策略你来定，说清楚它在存储量和分叉耗时上的代价。另外要能查通道的当前状态、已处理的批次列表，以及任一时间段内的应力曲线。

现有的材料档和作业接口保持原样，已有作业的提交方式和返回结果都不能变。

验收时会逐条看：
1. 取一条作业接口能接受的分段线性历程，按采样点拆成若干批依次追加到恒温通道，应力与作业接口对同一历程、同一时刻给出的结果一致，相对误差在 1e-9 以内（应力接近零处看绝对误差）；换一种切批方式，结果不变。
2. 恒温且等于参考温度时，结果与去掉 WLF 的同参数材料相同；恒温 T 时，与作业接口指定温度 T 的结果一致。
3. 先在参考温度下推进一段、再升温继续推进：升温前与恒温参考温度的对照通道逐点相同，升温后应力向 E∞·ε 靠拢的速度明显快于对照通道。
4. 变温通道把采样加密一倍，同一时刻的应力随加密收敛，README 附上你实测的收敛数据。
5. 同序号同内容重发，返回相同结果，通道当前时刻不变；同序号不同内容、跳号、时间倒退都返回带原因的错误，报错后通道状态与报错前逐字段相同。
6. 对同一通道并发发起多批序号连续的追加，全部完成后的结果与串行逐批追加一致，这一点要有测试覆盖。
7. 从某批末尾分叉后，两条通道各追加不同的后续：原通道的结果和从没分叉过一样；分叉通道在分叉点之前的应力与原通道相同，分叉点之后与「从头一路追加它全部数据的单条通道」一致。
8. 追加若干批后重启应用容器，接着追加的结果与不重启时完全相同。
9. 引用不存在的材料档、采样时间不严格递增、空批次、某个温度让 WLF 分母非正，都返回说明原因的错误，且不改动通道。

以上条目用 Jest 测试覆盖。重启续算在测试里可以用状态落库再读回来代替真实重启，但要能在 compose 环境下照 README 手动复现一次。部署沿用现有的 docker-compose 编排，不新增服务。
